## Rewrite tests

Each test showed the same content written two ways that differed in one respect. The content was illustrative.

1. Opening. A: argument first. B: scene first.
   Picked A. "But they keep telling me it should be B."
2. Sentence rhythm. A: short sentences. B: longer sentences.
   Picked A. "But can't read as too abrupt when read aloud, so the brain doesn't feel harried."
3. Register. A: plain. B: elevated and moral.
   First said "Hybrid." Of a hybrid with B's moral line: "Kinda sounds pandering and LinkedIn thought-leadery." Final pick A: "This personalizing feels so unearned to me."
4. Wit. A: straight. B: one dry line at the end.
   Picked A. "Only because when I saw vendors use B, I saw at least one customer think 'what a load of crock,' and that customer turned out to be the one I resonated with the most." (personal remainder omitted)
5. Naming the pattern. A: described. B: named ("governance drift").
   "Both actually," then "B most times, because it uses fewer words."
6. Certainty. A: flat ("breaks," "every team"). B: qualified, with "in the setups I've seen."

## Lessons from posts

### CI/CD post, "CI/CD for Lakebase synced tables: grants that come back on deploy" (2026-10-14)

The user read the first Google Doc draft and said: "the beginning is kinda abrupt as is the title, will an LLM find this will a Google search find this? Have you looked at any existing Community posts?" Then: "note all these down as lesson learned ... as something to keep in mind for future blogs."

- The draft title was "Grants that come back on deploy": the named pattern alone, with no product or task word. The most-read Community Lakebase posts lead with both (for example "How to perform Semantic Search in Databricks Lakebase", 9,792 views when read on 2026-10-14). The user picked "CI/CD for Lakebase synced tables: grants that come back on deploy", which keeps the name after a colon.
- The draft opened on `terraform apply`. The closest Community post opens with one sentence that says what Lakebase is. The new opening says what synced tables are and who hits the two failures, then gives the argument.
- The draft already quoted exact error text, which was kept and moved closer to the top.
- The first fix still failed. The second opening defined synced tables in one clause and then went straight to the two failures; the situation ("a common way to ship one is Terraform, then psql by hand") sat three paragraphs down. The user: "The beginning has to freaking make sense to a reader as to what will be going on. The beginning paragraph you had here was so mind bogglingly abrupt." The Medium shape (situation, complication, question, answer) was already in this skill and was skipped. The mechanic now says the opening paragraph IS the situation, with a stranger check.

### Payer-search post 1, LinkedIn article, "I let Genie Code run five experiments on Lakebase branches of my production database" (2026-10-14/15)

The user commented on the Google Doc review copy, two rounds. Each comment, verbatim, with what changed:

- On the opening ("Genie Code ... tested 5 changes to a search API over 3,000,000 rows"): "Or do I say I got my testing done rapidly using Genie Code and Lakebase and add a note about what Lakebase is also. What was I testing?" The opening now says the goal (find the right insurer more often), what the API does, and what Lakebase is, before any branch detail.
- On "One option cleared the bar": "Of the 5?"
- On "That left 10.5 queries, against the 9.2 needed to count as a win": "Where did we declare the parameters of the experiment t/ How does the reader know 9.2 counts as a win and what is special about 9.2". The rule now comes before the result, and 9.2 is shown as 1% of 920.
- On "Genie Code brought me the winner, its risks and one question": "what did it propose? Very unclear throughout this post just what it is we changed on Lakebase." On "re-applies the SQL": "same as above, must be some sort of ddl yeah, no need to show exact code but at least give them an indicatio of what it is we changed in each of the branches yeah?" The post now lists the 5 changes in plain words, and says one adds rows and four change one line of the search function.
- On "Genie Code also got something wrong: it checked only 3 of its 6 branch safety settings": "I don't know that I want this, given I am a Databricks SA." Offered a cut or a reframe as a reader tip; the user: "Cut it in both. I am a Databricks SA for crying out loud." A 14-seat review panel had kept this line as a mark of honesty, and Claude had recommended keeping it twice. That was the wrong call for the user's role.
- On the disclosure line: "Don't need this for LinkedIn. It is right in my bio."

The pattern across the comments: the draft was accurate and every number was sourced, but it assumed the reader already knew the experiment. It never said plainly what was tested, what each option changed, or what the bar was before showing the result.

Open question raised by this post: the mechanics say "never use lists in LinkedIn posts". This was a LinkedIn article, and the 5 changes went in as a bulleted list (a real set, as the Medium rule allows). Whether a LinkedIn article follows the LinkedIn-post rule or the Medium-article rule is the user's call. Answered 2026-10-15: LinkedIn articles follow the Medium-article rule, so a list of a real set is allowed.
- Chat, 2026-10-15, on the first plain list of the 5 changes ("add 287 rows to the synonym table…", "the BM25 keyword score counts 1.5 times"): "I think this migt be too inside baseball, maybe we make it less technical and broader while making it obvious these are changes on the index or some other object in PG?" Applied in both posts: each line says what the change does in plain words and names the Postgres object (synonym table or search function); algorithm names and settings were cut from post 1, and post 2 keeps only a short number tail ("50 instead of 100"). Became the "describe by what it does" mechanic.
